# MiraTech

## Что делаем сейчас

Делаем **базовый MVP** для специалиста по платному трафику (таргетолог/директолог), чтобы реально убрать рутину в запуске рекламы в **VK Ads** и **Яндекс Директ**.

Принцип простой: сначала делаем рабочую базу, которая экономит время каждый день. Новые фичи докидываем по ходу, когда увидим живой usage и узкие места.

## Цель MVP

За 1 интерфейс и 1 сценарий закрыть путь:
**бриф -> черновики кампаний -> согласование -> запуск -> базовый контроль после старта**.

Идея: специалист не кликает одно и то же по 100 раз, а управляет процессом и принимает ключевые решения.

## Scope MVP (что входит)

### 1) Бриф и подготовка
- чат-форма брифа: продукт, ЦА, гео, KPI, бюджет, ограничения;
- шаблоны naming convention и UTM;
- валидация входных данных до генерации (чтобы не стрелять себе в ногу на старте).

### 2) Генерация структуры и креативной основы
- автогенерация структуры: кампания -> группа -> объявление;
- генерация вариантов текстов/офферов под сегменты;
- адаптация формулировок под VK Ads и Яндекс Директ.

### 3) Запуск в рекламные кабинеты
- выгрузка через API в режиме черновиков;
- сценарий согласования: предпросмотр изменений + подтверждение;
- публикация с контролем лимитов и расписаний.

### 4) Базовая оптимизация после запуска
- алерты по просадкам/аномалиям (CPA, CPC, CR, скорость открутки);
- rule-based действия (пауза, корректировка ставки, уведомление);
- короткий ежедневный summary по кампаниям.

## Что НЕ входит в MVP

Чтобы не размывать фокус, пока не делаем:
- автономные AI-кампании без подтверждения человека;
- сложные мультишаговые playbook-сценарии;
- глубокие интеграции с CRM/сквозной аналитикой;
- продвинутые ML-прогнозы и авто-эксперименты.

## Архитектурная база (минимально достаточная)

- **Backend orchestration**: управление пайплайном брифа, генерации и публикации.
- **Интеграции**: коннекторы к API VK Ads и Яндекс Директ.
- **LLM-слой**: генерация текстов, проверка структуры и объяснение рекомендаций.
- **Rule engine**: исполняемые правила оптимизации в формате if/then.
- **UI/бот**: экран согласования + Telegram-уведомления.
- **Хранилище**: проекты, шаблоны, версии изменений, журнал действий.

## План реализации MVP (4-6 недель)

### Неделя 1
- финализация схемы брифа;
- шаблоны структуры кампаний и UTM;
- проектирование API-слоя интеграций.

### Неделя 2-3
- генератор структуры и текстов;
- предпросмотр и ручное редактирование;
- создание черновиков в VK Ads/Яндекс Директ.

### Неделя 4
- согласование и публикация;
- лимиты/валидации безопасности;
- базовый лог действий.

### Неделя 5-6
- rule-based оптимизация;
- алерты и daily summary;
- стабилизация, фиксы, полировка UX.

## KPI MVP (как поймем, что взлетело)

- сокращение времени от брифа до запуска минимум на **40%**;
- минимум **70%** кампаний запускаются через новый сценарий без ручной сборки “с нуля”;
- снижение числа типовых ошибок запуска (UTM/naming/настройки) минимум на **50%**;
- ежедневные отчеты и алерты покрывают 100% активных кампаний в MVP-контуре.

## Принципы

- человек в контуре: AI предлагает, человек подтверждает;
- прозрачность: каждое авто-действие можно объяснить;
- безопасность: лимиты, права, аудит-лог;
- прагматизм: сначала value, потом “космос”.

## Бэклог после MVP (докидываем по ходу)

- AI-рекомендатель бюджетов и ставок;
- авто A/B-тесты креативов и сегментов;
- интеграция с CRM и сквозной аналитикой;
- детектор креативной усталости и авто-ротация.

## Как проверить работоспособность через GitHub (если нет локального Git)

Ниже сценарий только через сайт GitHub, без установки чего-либо на компьютер.

### 1) Проверка, что код вообще обновляется
1. Открой репозиторий на GitHub.
2. Перейди во вкладку **Code** и открой `README.md`.
3. Нажми **History** (вверху файла) и проверь, что есть последние коммиты с обновлением MVP-плана.
4. Зайди в нужный коммит и открой вкладку **Files changed**. Там видно, что именно поменялось.

### 2) Проверка через Pull Request
1. Перейди во вкладку **Pull requests**.
2. Открой последний PR.
3. Проверь:
   - описание PR (что сделано и зачем);
   - вкладку **Files changed** (нет ли странных/лишних изменений);
   - статус checks (если подключены CI-проверки).
4. Если все ок, нажми **Merge pull request** -> **Confirm merge**.

### 3) Базовая sanity-проверка после merge
1. После merge вернись в ветку `main` (или рабочую дефолтную ветку).
2. Открой `README.md` и убедись, что там актуальная версия документа.
3. Во вкладке **Commits** проверь, что merge-коммит появился в истории.

### 4) Если появится код (не только документация)
Когда начнем добавлять backend/frontend, проверка через сайт будет такой:
- смотри статус **Actions** (workflow должен быть зеленым);
- в PR проверяй, что тесты прошли;
- при наличии превью-деплоя (например, Vercel/Render) открывай ссылку из PR и кликай базовый сценарий руками.

### 5) Мини-чеклист перед нажатием Merge
- PR маленький и понятный, без “смешали все в кучу”;
- в описании есть цель, изменения, как проверяли;
- нет красных CI-checks;
- нет конфликтов с веткой `main`;
- ты понимаешь, что именно попадет в прод.

Если кратко: для текущего этапа (документация) тебе достаточно проверять **History + PR Files changed + Merge**. Этого более чем достаточно, чтобы уверенно двигаться без локальной установки Git.


## Если вообще с нуля: что нажимать прямо сейчас (5 минут)

Окей, максимально просто. Твоя задача сейчас: убедиться, что изменения попадают в репу и их можно безопасно принять.

1. Зайди в репозиторий на GitHub.
2. Нажми сверху **Pull requests**.
3. Открой самый свежий PR (самый верхний в списке).
4. В PR открой вкладку **Files changed**.
5. Убедись, что изменился только `README.md`.
6. Пролистай вниз и нажми **Approve** (если есть кнопка review) или просто переходи дальше.
7. Нажми **Merge pull request**.
8. Нажми **Confirm merge**.
9. Нажми **Code** -> выбери ветку `main`.
10. Открой `README.md` и проверь, что текст обновился.

Готово. Это и есть базовая проверка работоспособности на текущем этапе.

### Если кнопка Merge не нажимается
- есть красные проверки в PR -> открой вкладку **Checks/Actions**, посмотри ошибку;
- есть конфликт -> нажми **Resolve conflicts** (или попроси меня подготовить новый PR без конфликта);
- нет прав на merge -> попроси владельца репозитория дать доступ `Write` или `Maintain`.

### Как понять, что все ок
- PR в статусе **Merged**;
- коммит виден в `main`;
- в `README.md` на `main` новый текст.
